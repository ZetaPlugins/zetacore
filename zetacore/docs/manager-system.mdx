ZetaCore's manager system lets you wire dependencies with annotations instead of manual setup code.
At the center is `ManagerRegistry`, which creates manager instances, injects dependencies, and handles lifecycle callbacks.

This guide walks through the common setup and usage patterns.

## Quick Start

Here is a basic setup in your plugin `onEnable` method:

```java
public final class MyPlugin extends JavaPlugin {
    private ManagerRegistry managerRegistry;

    @Override
    public void onEnable() {
        managerRegistry = new ManagerRegistryBuilder()
                .setPlugin(this)
                .setPackagePrefix("com.example.myplugin")
                .setRequireManagerAnnotation(true)
                .build();

        // Instantiates eager singleton managers
        managerRegistry.initializeEagerManagers();

        UserService userService = managerRegistry.getOrCreate(UserService.class);
    }
}
```

In this example, the registry is built once, eager singleton managers are initialized, and services are resolved on demand.

## What You Get

With this setup, you get:

- Manager creation and caching
- Field injection for manager dependencies
- Plugin instance injection
- Post-construction lifecycle hooks
- Optional eager startup for selected managers
- Optional strict mode requiring `@Manager`

## Declaring Managers

Here is a default singleton manager:

```java
@Manager
public class UserService {
}
```

Here is a prototype manager that creates a new instance for each request:

```java
@Manager(scope = ManagerScope.PROTOTYPE)
public class RequestContext {
}
```

Here is an eager singleton manager, created during startup initialization:

```java
@Manager(eagerlyLoad = true)
public class CacheWarmupService {
}
```

## Injection

Inject another manager using `@InjectManager`:

```java
@Manager
public class ProfileService {
    @InjectManager
    private UserService userService;
}
```

Inject the plugin instance using `@InjectPlugin`:

```java
@Manager
public class ConfigService {
    @InjectPlugin
    private JavaPlugin plugin;
}
```

In this setup, `ProfileService` receives `UserService` automatically, and `ConfigService` receives the active plugin instance.

Keep in mind:

- `@InjectPlugin` fields must be `JavaPlugin` (or subclass).
- `@InjectManager` resolves from the registry by field type.

## Post Construction Hook

Use `@PostManagerConstruct` for initialization logic that should run after injections are complete:

```java
@Manager
public class ProfileService {
    @InjectManager
    private UserService userService;

    @PostManagerConstruct
    private void init() {
        // Called after manager/plugin injection
    }
}
```

This is useful for setup that depends on injected fields.

Rules:

- Method must have zero parameters.
- Private methods are supported.

## Scope Semantics

`ManagerScope` controls how instances are created:

### `SINGLETON`

- One shared instance per type in the registry
- Created once and reused

### `PROTOTYPE`

- New instance every time `getOrCreate(...)` is called
- Not cached as a singleton

## Constructor Resolution

When `ManagerRegistry` creates a manager, it checks constructors in this order:

1. Single-argument constructor compatible with your plugin class or `JavaPlugin`
2. No-argument constructor

If neither exists, creation fails.

## Eager Initialization

`initializeEagerManagers()` scans the configured package and creates only managers that are:

- Annotated with `@Manager`
- Marked `eagerlyLoad = true`
- In `SINGLETON` scope

Prototype managers are not eagerly initialized.

## Manual Registration and Injection

If you already created an object yourself, you can still register or inject it.

Register a pre-built instance:

```java
managerRegistry.registerInstance(existingService);
```

Register under an explicit key type:

```java
managerRegistry.registerInstance(ServiceInterface.class, existingServiceImpl);
```

Inject dependencies into objects not created by the registry:

```java
SomeListener listener = new SomeListener();
managerRegistry.injectManagers(listener);
```

This is useful for listeners, command executors, and tab completers.

## Integration with Auto Registrars

Both `AutoEventRegistrar` and `AutoCommandRegistrar` accept a `ManagerRegistry`.
When provided, they inject dependencies before registration.

```java
ManagerRegistry registry = new ManagerRegistryBuilder()
        .setPlugin(this)
        .setPackagePrefix("com.example.myplugin")
        .setRequireManagerAnnotation(true)
        .build();

registry.initializeEagerManagers();

new AutoEventRegistrar.Builder()
        .setPlugin(this)
        .setPackagePrefix("com.example.myplugin")
        .setManagerRegistry(registry)
        .build()
        .registerAllListeners();

new AutoCommandRegistrar.Builder()
        .setPlugin(this)
        .setPackagePrefix("com.example.myplugin")
        .setCommandNamespace("myplugin")
        .setManagerRegistry(registry)
        .build()
        .registerAllCommands();
```

    This keeps your command and listener classes clean while still allowing manager injection.

## Error Handling and Common Failures

### Class is not annotated with `@Manager`

Cause: strict mode is enabled and the requested/injected class has no `@Manager`.

Fix: add `@Manager`, or set `setRequireManagerAnnotation(false)`.

### No suitable constructor found

Cause: class has neither a no-arg constructor nor a plugin-compatible constructor.

Fix: add one of the supported constructor shapes.

### Invalid `@InjectPlugin` field type

Cause: field is not `JavaPlugin` or subclass.

Fix: change the field type.

### Invalid `@PostManagerConstruct` signature

Cause: method has parameters.

Fix: make it a zero-argument method.

### Circular dependency detected

Cause: dependency cycle (for example, `A -> B -> A`).

Fix: break the cycle by refactoring dependency flow.

## Best Practices

- Enable strict annotation mode in production plugins.
- Keep package scanning scope narrow (`setPackagePrefix(...)`).
- Use singleton for long-lived services.
- Use prototype for request-like or temporary objects.
- Keep post-construct methods idempotent where possible.
